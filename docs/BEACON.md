# 동방 비콘 자동 감지 (HE5)

## 구조

```
HE5 (iBeacon 송출)
  → 회원 휴대폰의 SAI ROOM 앱 (Android/iOS 네이티브 플러그인 SaiBeacon)이 신호 세기(RSSI) 수신
  → js/beacon.js 가 입실·유지·퇴실 판단 (연속 확인, 히스테리시스, 신호 끊김 유예)
  → POST /api/v1/me/beacon-presence  (로그인 세션 쿠키 + CSRF, 사용자 ID는 서버가 세션에서 결정)
  → 서버가 DB(SQLite 또는 PostgreSQL)에 회원·기기별 마지막 감지 시각을 서버 시계로 저장
  → 승인 회원 1명당 1명으로, 퇴실 유예시간 안의 기록만 집계 (직접 입실 기록과 중복 없이 합산)
  → 홈 화면이 기존 30초 주기 조회로 인원수·게이지 갱신
```

- **비폰 매니저**는 운영진이 HE5를 검색·설정하는 도구일 뿐입니다. SAI ROOM은 비폰 매니저와 연결하지 않고, 그 데이터를 가져오지도 않습니다.
- UUID·Major·Minor는 공개적으로 송출되는 **방 식별값**입니다. 비밀번호나 출입 인증 수단이 아닙니다. 로그인한 회원이 앱을 조작해 거짓 "감지"를 보낼 가능성은 남아 있습니다. 그래서 이 인원은 동아리 현황 참고용으로만 쓰고, 출석·출입 증빙으로 쓰지 마세요.
- 홈의 숫자는 **앱으로 감지·입실한 회원 수**이며 실제 전체 방문자 수가 아닙니다. 홈 화면에도 이렇게 표시됩니다.

## 1. 비폰 매니저에서 식별값 확인 (운영진)

비폰 매니저(현승)는 주변 iBeacon을 검색하고, 비콘별 RSSI를 그래프로 보여주며, 연결해서 UUID·Major·Minor를 수정하는 기능을 제공합니다([App Store 설명](https://apps.apple.com/pa/app/%EB%B9%84%ED%8F%B0-%EB%A7%A4%EB%8B%88%EC%A0%80/id6587572468)). 화면 메뉴 이름은 앱 버전에 따라 다를 수 있으니 실제 앱 화면을 기준으로 하세요.

1. HE5 전원을 켜고 동방 안에서 비폰 매니저를 실행합니다.
2. 검색 목록에서 HE5를 찾습니다. 휴대폰을 HE5에 가까이 대면 RSSI가 가장 강한(숫자가 0에 가까운) 항목입니다.
3. 해당 비콘의 **UUID**(8-4-4-4-12 형식), **Major**, **Minor**를 기록합니다.
4. 같은 UUID를 쓰는 다른 비콘이 근처에 있으면 Major·Minor로 동방 비콘을 구분합니다. 필요하면 비폰 매니저에서 동방 전용 값으로 바꿉니다.
5. RSSI 그래프로 아래 기준값을 정할 수 있습니다. 동방 안 여러 자리와 복도에서 각각 RSSI를 확인해 두세요.

## 2. SAI ROOM에 등록 (운영진·관리자만)

앱 **설정 → 동아리 운영 → 동방 비콘 등록·설정** (`#beacon-settings`)

| 항목 | 초깃값 | 의미 |
| --- | --- | --- |
| 자동 감지 사용 | 꺼짐 | 켜야 회원 앱이 감지하고 서버가 받습니다. UUID가 있어야 켤 수 있습니다. |
| UUID | (비어 있음) | **실제 값 입력 필요.** 비폰 매니저에서 확인한 값 |
| Major / Minor | (비어 있음) | 비우면 해당 UUID의 모든 값 허용. Minor만 입력할 수는 없습니다. |
| 입실 신호 기준 | -75 dBm | 이보다 강한 신호가 연속 2회(15초 안) 잡혀야 입실 |
| 유지 신호 기준 | -85 dBm | 입실 후에는 이 값까지 유지 (입실 기준보다 약해야 함) |
| 갱신 간격 | 30초 | 휴대폰이 서버에 상태를 다시 보내는 간격 |
| 퇴실 유예시간 | 120초 | 이 시간 동안 갱신이 없으면 서버가 인원에서 제외 (갱신 간격의 2배 이상) |
| 기준 인원 | 15명 | 게이지가 가득 차는 인원. 초과해도 숫자는 정확히 표시하고 게이지만 최대로 유지 |

**신호 기준과 시간 값은 모두 테스트용 초깃값입니다.** 처음 저장하기 전까지 화면에 "테스트용 초깃값" 경고가 표시됩니다. 동방 구조, HE5 송출 세기, 설치 위치에 따라 아래 검증 순서대로 조정하세요. UUID·Major·Minor를 바꾸거나 자동 감지를 끄면, 이전 비콘 기준의 감지 기록은 즉시 지워집니다.

## 3. 지원 범위

| | Android (Capacitor 앱) | iOS (Capacitor 앱) | 웹 브라우저 |
| --- | --- | --- | --- |
| 감지 방식 | BluetoothLeScanner + 하드웨어 필터 (Apple 제조사 데이터 0x004C) | Core Location 비콘 레인징 (`CLBeaconIdentityConstraint`) | 불가 |
| 필요 권한 | Android 12+: 근처 기기(BLUETOOTH_SCAN) + 위치 / 11 이하: 위치 | 앱 사용 중 위치 허용 | — |
| 앱 화면이 켜져 있을 때 | 지원 (저지연 스캔) | 지원 | "사용 불가" 안내 |
| 앱이 백그라운드·화면 잠금일 때 | 저전력 스캔으로 전환. OS가 늦추거나 멈출 수 있고 WebView도 멈출 수 있어 **주기 전송 보장 없음** | iOS가 레인징을 멈춤 → **전송 안 됨** | — |
| 블루투스 상태 확인 | 켜짐/꺼짐 감지, 꺼지면 즉시 퇴실 전송, 다시 켜면 자동 재개 | Core Location이 블루투스 상태를 알려주지 않음 → 신호가 끊긴 것으로 처리되어 시간이 지나면 퇴실 | — |
| 권한 해제 | OS가 앱을 재시작 → 재실행 시 "권한 필요" 안내 | 즉시 감지해 퇴실 전송 후 "권한 필요" 안내 | — |

백그라운드에서 자리를 비우면 서버가 퇴실 유예시간 뒤 자동으로 인원에서 제외합니다. 앱으로 돌아오거나 네트워크가 복구되면 즉시 상태를 다시 확인해 전송합니다.

백그라운드 상시 감지는 **의도적으로 구현하지 않았습니다.** Android는 포그라운드 서비스와 백그라운드 위치 권한, iOS는 "항상 허용" 권한과 지역 모니터링이 추가로 필요하고, 스토어 심사·배터리·개인정보 부담이 큽니다. 필요하면 별도 작업으로 진행하세요.

### 배포 방식 (중요)

모바일 앱은 서버가 제공하는 기존 웹 화면을 `SAI_APP_URL`에서 그대로 불러옵니다(Capacitor `server.url`). 이렇게 하면 같은 출처의 쿠키 세션, CSRF, 화면을 바꾸지 않아도 되므로 CORS를 열지 않았습니다.

Capacitor 문서는 `server.url`을 라이브 리로드용이며 운영용으로 의도되지 않았다고 안내합니다. 원격 웹만 감싼 앱은 App Store 심사(가이드라인 4.2)에서 거절될 위험도 있습니다. 동아리 내부 배포라면 다음 경로가 현실적입니다.

- Android: APK 직접 설치
- iOS: TestFlight 또는 개발자 기기 설치

정식 스토어 배포가 필요하면 웹 파일을 앱에 포함하고 API를 원격으로 호출하는 구조로 바꿔야 합니다. 이 경우 교차 출처 인증, CORS, iOS 쿠키 정책 변경이 필요합니다.

## 4. 실기기 설치

준비물:

- Node 22+
- Android: Android Studio(SDK 36), USB 디버깅을 켠 Android 7.0+ 기기
- iOS: Mac, Xcode 16+, Apple 개발자 계정, iOS 15+ iPhone
- 서버는 PC와 휴대폰이 같은 와이파이에 있거나, HTTPS 운영 주소여야 합니다.

```sh
npm ci
# 1) 서버 (PC의 LAN IP가 192.168.0.10인 예)
SAI_PUBLIC_ORIGIN=http://192.168.0.10:5317 python -m uvicorn main:app --app-dir sai-room-backend --host 0.0.0.0 --port 5317
# 2) 앱에 서버 주소 반영 (주소를 바꿀 때마다 다시 실행)
SAI_APP_URL=http://192.168.0.10:5317 npx cap sync
# 3) 실행
npx cap open android   # Android Studio에서 기기 선택 후 Run
npx cap open ios       # Xcode에서 Signing 팀 지정 후 Run
```

- `http://` 주소는 같은 네트워크에서 테스트할 때만 쓰세요(평문 통신 허용). 운영은 `SAI_APP_URL=https://실제-도메인`입니다.
- 서버에 `SAI_ENV=production`이 설정돼 있으면 시뮬레이터가 비활성화되고, 서버도 시뮬레이터 신호를 거절합니다.
- 앱 실행 → 로그인 → **설정 → 동방 자동 감지 → 자동 감지 켜기** → 권한 허용.
- 네이티브 iBeacon 해석 테스트: `cd android && ./gradlew test` (`IBeaconParserTest`)

## 5. 실기기 검증 순서

각 단계에서 운영진 기기의 **설정 → 동방 비콘 등록·설정** 값과 홈 인원수, 회원 기기의 감지 화면 상태를 기록하세요.

1. **등록 확인**: 운영진이 UUID·Major·Minor 입력 → 저장 → "테스트용 초깃값" 경고가 사라지는지 확인.
2. **동방 내부**: 회원 A가 동방 안에서 자동 감지 켜기 → 약 2~15초 안에 "동방에서 감지됨" → 운영진 홈 인원 +1 (최대 30초 주기 갱신, 새로고침 시 즉시).
3. **두 번째 회원**: 회원 B 기기에서도 반복 → 2명. 회원 A가 기기 두 대로 켜도 1명 유지.
4. **동방 안 위치별 RSSI**: 감지 화면은 상태만 보여주므로, 비폰 매니저로 동방 구석·문 앞 RSSI를 측정해 입실 기준을 정합니다.
5. **복도**: 문 밖 복도에서 "신호 찾는 중/신호 약함"이 유지되고 인원에 들어가지 않는지 확인. 복도에서 입실로 잡히면 입실 기준을 강하게(예: -75 → -70) 조정.
6. **잠깐 가림**: 동방 안에서 휴대폰을 주머니에 넣거나 손으로 가려 1분 정도 둠 → 인원이 출렁이지 않는지 확인. 자주 빠지면 유지 기준을 약하게(-85 → -90) 하거나 퇴실 유예시간을 늘림.
7. **화면 잠금 / 백그라운드**: 동방 안에서 화면을 잠그고 3분 대기 → 운영진 홈에서 회원이 퇴실 유예시간 뒤 빠지는지 기록. iOS는 빠지는 것이 정상입니다. Android는 기기마다 다르므로 결과를 기록. 다시 앱을 열면 곧 재입실되는지 확인.
8. **퇴실**: 앱을 연 채 동방 밖으로 나가 걸어감 → 약 90초 뒤 앱이 퇴실을 전송하고 인원 -1. 자동 감지 끄기·로그아웃 시 즉시 -1.
9. **블루투스 끄기 / 권한 해제**: 동방 안에서 블루투스 끄기 → Android는 즉시 퇴실 + "블루투스 꺼짐", 다시 켜면 자동 재개. iOS는 유예시간 뒤 퇴실. 앱 설정에서 위치 권한 해제 → "권한 필요" 안내.
10. **서버 장애**: 서버 중지 → 회원 앱 "전송 실패", 운영진 홈 "갱신 지연" 표시 확인 → 서버 재시작 후 자동 복구 확인.

조정 원칙: 복도에서 잡히면 **입실 기준을 강하게**, 동방 안에서 자주 빠지면 **유지 기준을 약하게 하거나 퇴실 유예시간을 늘리세요**. 퇴실 유예시간을 길게 하면 실제로 나간 사람이 늦게 빠집니다.

## 6. 개발용 감지 시뮬레이터

개발 서버(`SAI_ENV`가 production이 아님)에서만 **설정 → 동방 자동 감지** 아래에 "개발 모드 전용 · 감지 시뮬레이터"가 나타납니다.

- 실제 BLE 드라이버와 같은 인터페이스로 강함·경계·약함·끊김 신호를 1초마다 만들어 **본인 계정의 감지만** 보냅니다.
- 요청에는 `source: "simulator"`가 붙고, 운영 서버는 이를 403으로 거절합니다.
- 인원수를 직접 바꾸는 API나 버튼은 없습니다.

시뮬레이터로 숫자가 바뀌는 것은 화면·서버 흐름 확인일 뿐이며, 실제 비콘 연동 검증이 아닙니다.

## 7. 운영 전 남은 작업

- 실제 HE5 식별값 등록과 위 실기기 검증 (아직 미완료)
- 앱 아이콘·이름·번들 ID(`SAI_APP_ID`, 기본 `kr.ac.sejong.sai.room`) 확정, Android 서명 키 생성(저장소에 올리지 말 것), iOS 서명 팀 지정
- 배포 경로(내부 설치 vs 스토어) 결정 — 스토어라면 위 "배포 방식" 구조 변경 필요
- 운영 PostgreSQL에 `sai-room-backend/migrations/postgres/002_beacon_presence.sql` 적용
